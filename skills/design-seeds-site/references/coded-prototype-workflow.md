# Coded prototype workflow

Use this workflow for a new visual direction or a major redesign.

## Diagnose the current interface

Record specific failures in composition, hierarchy, typography, color, imagery, interaction, density, and responsive behavior. Distinguish structural problems from palette preference. Do not begin by editing color variables; a palette change cannot repair weak composition.

## Define materially different directions

Each direction needs its own spatial model, typographic hierarchy, image behavior, interaction character, density, rhythm, and surface logic. Two alternatives that differ only in color are one design.

## Build in isolated code

Use semantic HTML, CSS, and only the JavaScript needed for representative behavior. Use real copy and existing approved assets. Prototype both the story atlas as a reader invitation and Project Explorer as a working authorship instrument.

Required behavior includes a functional mobile menu, links between the prototype surfaces, visible focus states, and at least one representative content interaction. Do not connect prototype CSS or scripts to production templates.

## Test the composition

Review at 320, 375, 430, 768, 1024, and 1440 CSS pixels, including short and tall mobile viewports. Use real text scaling and long file paths.

At each width, ask:

- Is the purpose understandable before scrolling?
- Is there one clear visual entry point?
- Does imagery participate in the composition?
- Is the page recognizably Seeds of the Throne without its title?
- Does the design still work when content is long?
- Does the mobile page feel intentionally composed?

## Capture evidence and request selection

Save viewport screenshots and a short QA report. Present direct URLs to every working prototype. A concept name, mood board, or static image does not count as approval.

## Translate to production

Only after selection, extract semantic color and type tokens, layout primitives, navigation behavior, hero composition, section patterns, image treatments, motion rules, and page variants. Then implement in small verified stages without regressing production functionality.
